## Порядок работы (решение владельца, 22.11.2026)

- **Один шаг = один маленький PR**: сделали фикс → владелец проверил → задеплоил → следующий шаг.
- Детали шага обсуждаются **только непосредственно перед его выполнением**, а не весь план сразу.
- Каждый шаг — с ветки от свежего `origin/main`, с тестом.

## Поправки к ТЗ SEO-агента (что проверено и оказалось иначе)

1. **Перекос витрины (задача 1) — данные, а не алгоритм.** Сортировка = `rent_model_web.sort_n`
   (ручное поле, редактируется в `bb/kr_baza_new.php`). 28 моделей с отрицательным `sort_n` (−200…−60) —
   все женские (кат. 61 платья, 145 снежинки, 165 снегурочки) → «18 платьев, 0 мальчиков».
   Сортировке ~10 лет, владелец разрешил переделать как нужно для равномерной витрины.
   `m_sex` у многих моделей не заполнен — баланс «по полу» не может опираться только на него.
2. **Нестабильная пагинация (ТЗ не заметило).** 167 моделей с `sort_n=0`; `usort` в PHP 7.4 нестабилен,
   SQL сортирует по `free_num`, который меняется при каждой выдаче → стр. 1/2 могут дублировать/терять карточки.
3. **Дубли «104, 104» — разные варианты, не ошибка выборки.** `tovar::getRostSizeArrayByModelId()` уже
   уникализирует по (rost_from, rost_to, size). Склеивать их в модалке брони нельзя (сервер ищет свободные
   экземпляры по rost_from/rost_to) — подписывать диапазоном «98–104». Дублей карточек в листинге нет:
   1 карточка = 1 модель (проверено: 381 модель, повторов названий 0).
4. **JS-падение при выборе даты возврата — корень в `bb/Schedule.php`.**
   `getDateOpenCloseHoursArrayForPreiod()` идёт по дням со временем `from_kb`; если час `to_kb` < часа
   `from_kb`, последний день не попадает в `.schedule`, а `KBForm::getToDaysArray()` его показывает →
   `scheduleInput` = null. Null-guard в `timeChange()` — только страховка.
5. **Фильтр по дате — мёртвый код:** `eventDate` передаётся в `Model`, но нигде не используется → удалить блок.
6. **`llms.txt` перепутан сильнее, чем в ТЗ:** `halloween-costumes` = «Воины, разбойники»,
   `accessories` = «Флора и фауна», `kostumy-zverei` = «Сказки, мультики»,
   `karnavalnye-kostyumy-boys` = «Тематические», `detskie-nariady-prokat` = «Детская вечерняя мода»;
   нет «Королевство», «Профессии», «Народные, этно». Переписывать по БД. Моделей 381 (не 355).
7. **Слайдер:** первым сейчас Premium Start; `fetchpriority="high"` стоит на двух картинках.
8. **Порядок мобильных чипов — данные:** `sub_razdel.order_num_sub_razd` (Сказки=0, Новый год=1),
   правится в `bb/sub_razdel_manage.php` (влияет и на десктоп-меню).
9. **Тексты «line2» блоков карточки** (доставка, адрес, залог, тариф) — в БД `l3_karn_dop_fields`
   (`bb/page_management.php`); в Blade захардкожены только короткие значения line1.
10. **`l2.js`/`l3.js` версионируются вручную** (`?v=2`, `?v=15`) — при каждой правке поднимать версию,
    иначе Cloudflare отдаст старый файл.

## П. 3–5: витрина по спросу — принятые решения (22.11.2026)

Согласовано с владельцем: ранжировать по прошлогодним прокатам, `sort_n` в карнавале игнорировать (БД не меняется).

- **Спрос** = оплаченные прокаты (`rent_deals_arch` с `r_paid > 0`, плюс все `rent_deals_act`; `closed_loss` — тоже
  прокат, это закрытие с недоплатой) с выдачей в окне **[сегодня; +45 дней) год и два года назад**. Окно смотрит вперёд:
  в конце ноября поднимается декабрьский спрос, в октябре — Хэллоуин, без ручного флага сезона.
- **Среднее за годы, когда модель уже была** (самая ранняя `buy_date` экземпляров, включая выбывшие
  `tovar_rent_items_arch`; прокаты выбывших экземпляров тоже считаются). Модель, купленная в 2025, не делит свой спрос на 2.
- **Новинки** (куплены после начала прошлогоднего окна и без прокатов в окнах) — средний спрос своей категории
  (нет моделей с историей — среднее по категориям того же `cat_type`). Старые модели с 0 прокатов остаются с 0.
- **Пол**: `tovar_rent.m_sex`, иначе большинство экземпляров, иначе унисекс (унисекс баланс не нарушает).
- **Аксессуары** — по началу названия (аксессуар/акссесуар, маска, шляпа, корона, кокошник, колпак, валенки, парик,
  скипетр, меч, крылья, шарф…) или `dog_name = 'Аксессуар'`: всегда ниже полноценных костюмов (27 моделей сейчас).
- **Без фильтра**: жадный отбор — вес k-й карточки категории `score × 0.75^k`, категория не повторяется в 3 последних
  карточках, перевес мальчиков/девочек ≤ 2; ограничения ослабляются, если выбрать не из чего (страница одной категории).
- **С фильтром** (`gender`/`rost`): только рейтинг + аксессуары вниз.
- **Порядок детерминирован**: при равенстве — спрос за последние 365 дней, затем более новая модель (id ↓).
  Карта считается за ~55 мс по всем 1680 моделям и кэшируется до конца дня → стабильная пагинация в течение дня.
- **Отказоустойчивость**: ошибка расчёта → прежний порядок по `sort_n` + строка в лог, листинг не падает.
- **Не учитываются** (можно добавить позже): текущие брони сезона (`karn_brons`), выручка вместо числа прокатов.

## Отложено (не делать без отдельного решения)

- Новогодний первый слайд на главной — нужна картинка 1200×400 / 800×600; сдвиг Premium Start.
- Текстовая ссылка на карнавал на первом экране главной — вместе со слайдом.
- Чекбокс согласия на рассылку (Закон РБ № 99-З) + таблица `marketing_consents` — январь, отдельный PR.
- Быстрые чипы хитов («Мушкетёры», «Пираты», …) в мобильной ленте.
- Рефакторинг слагов категорий и облегчение JSON-LD — январь (guardrails ТЗ).

## Guardrails из ТЗ (соблюдаем)

Не менять слаги/каноникалы карнавала; не трогать JSON-LD листингов; SSR листинга (H1, текст, 24 карточки
с `<a href>`, пагинация `<a href>`) без JS; не удалять `<noscript>` Font Awesome; зелёные
`CarouselLoadingPriorityTest`, `CatalogLazyLoadingTest`, `FontLoadingTest`; сезонное — через один флаг
с автоотключением после 2027-01-10.
