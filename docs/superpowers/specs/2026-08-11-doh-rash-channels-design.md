# Design: `bb/doh-rash.php` — переход на каналы оплаты и польский дизайн

**Date:** 2026-08-11
**Status:** Draft — awaiting user review
**Scope:** только `bb/doh-rash.php` (+ один согласованный шаг в MCP API, см. «Смежные системы»)

---

## Проблема

Страница «Доходы-расходы» построена вокруг сети из четырёх офисов: сначала выбирается офис,
затем касса внутри него. Офис остался один (Литературная), поэтому:

- фильтр «Офис» и вложенный список касс — лишний шаг на каждой операции;
- в выпадающих списках висят закрытые точки (Склад, Победителей, Ложинская) и вторая
  курьерская касса — оператор может по ошибке провести деньги через несуществующую кассу;
- нет сейфа: наличные, которые физически лежат в сейфе, учитываются как остаток кассы.

Параллельно у польского проекта (`tiktakrent.pl`, локальная копия `~/sites/tiktakrentpl`) та же
страница уже переписана под один офис: плоский список каналов оплаты, современная вёрстка,
модальная форма. Белорусская версия должна выглядеть и работать так же.

## Решения, принятые с заказчиком (2026-08-11)

1. Курьерских канала было два (`cur`+`k1`, `cur`+`k2`) — остаётся **один** «Курьер».
2. Сейф — **не** полноценная касса с дневными остатками; он живёт только на этой странице.
3. Сейф виден тем же сотрудникам, что и Банк (`logpass_id` 2, 3, 5, 9).
4. Польский дизайн переносится **целиком**, включая плитки итогов и блок распределения по статьям.

## Каналы оплаты

Итоговый список в интерфейсе — пять пунктов:

| Пункт | `doh_rash.channel` | `doh_rash.kassa` | Комментарий |
|---|---|---|---|
| К1 | `1` | `k1` | бывшая касса 1 на Литературной |
| К2 | `1` | `k2` | бывшая касса 2 на Литературной |
| Банк | `bank` | `bank` | без изменений |
| Сейф | `safe` | `safe` | новый канал |
| Курьер | `cur` | `k1` | из двух курьерских касс остаётся одна |

### Почему сохраняем исторические коды, а не переходим на польскую схему

В польской версии `channel` всегда равен номеру офиса, а канал оплаты закодирован в `kassa`
(`k1`/`k2`/`card`). Соблазнительно повторить один в один, но в белорусской базе на текущую
кодировку опирается работающий код:

- `bb/doh-rash.php` скрывает банк от неруководителей условием `channel != 'bank'`;
- `bb/models/KassaOstatok.php` (дневные остатки, таблица `kassas`) выбирает операции запросом
  `... AND channel=$officeId AND kassa='$kassaType'` — причём `$officeId` подставляется **без
  кавычек**, то есть рассчитан на числовой офис;
- `FinanceEntriesController` (MCP API) валидирует пару `channel × kassa` по тем же правилам.

Переход на польскую схему сделал бы старые и новые записи несопоставимыми и потребовал бы
миграции данных. Поэтому кодировка в БД остаётся прежней, а «плоский список» существует только
в UI: преобразование делает одна функция.

### Архивные каналы

`2` (Ложинская), `3` (Победителей), `4` (Склад), `cur`+`k2` (Курьер 2) убираются из всех
выпадающих списков — и в фильтре, и в форме внесения. При этом:

- расшифровка названий (`of_print()` / `kassa_print()`) их по-прежнему знает, поэтому в таблице
  операций старые записи читаются как раньше;
- фильтр «Канал оплаты» = «все» показывает их наравне с активными — история не теряется.

**Остатки.** Заказчик подтвердил 2026-08-11: остатки на всех архивных каналах нулевые, переносить
деньги перед выкатом не требуется. Отдельная сверка не нужна.

### Сейф

Отличается от остальных каналов правилами доступа:

- на вкладках «Расход» и «Доход» его в списке каналов **нет**;
- на вкладке «Сдача в кассу» он доступен и как источник (`channel`), и как получатель (`type2`);
- виден только сотрудникам с `logpass_id` ∈ {2, 3, 5, 9} — тот же список, что у Банка;
- остаток по сейфу = сумма всех операций по нему, отдельной таблицы не заводим.

Ограничение «только через сдачу в кассу» проверяется **на сервере**, а не только в JS: при
`type1` ∈ {`rash`, `doh`} канал `safe` отклоняется. Иначе правило обходится подменой поля формы.

## Интерфейс

Переносим структуру польской страницы (`~/sites/tiktakrentpl/bb/doh-rash.php`), сохраняя
белорусские особенности.

**Структура сверху вниз:**

1. Шапка: заголовок «Расходы», период, круглая кнопка «+» справа.
2. Флеш-сообщение об успешной операции.
3. Фильтры одной карточкой: даты, быстрые пресеты (с начала года / этот месяц / прошлый месяц /
   30 дней), кнопка «Показать»; вторым рядом — «Канал оплаты», «Тип операции», «Статья»,
   «Сотрудник».
4. Плитки итогов: расходы, прочие доходы, сальдо.
5. Две колонки: слева таблица операций, справа распределение расходов по статьям с полосами.
6. Модальное окно внесения операции с тремя вкладками: «Расход» / «Доход» / «Сдача в кассу».

**Фильтр «Офис» удаляется.** Параметр `item_place` остаётся в форме скрытым полем со значением
`all` — на нём завязано скрытие банка от неруководителей, и его дешевле сохранить, чем
переписывать условие. Роль офисного фильтра берёт на себя «Канал оплаты», который фильтрует по
паре `channel` + `kassa`, а не по одной колонке, как раньше.

Условие скрытия для сотрудника без прав меняется с `channel != 'bank'` на
`channel NOT IN ('bank', 'safe')` — иначе сейф, невидимый в форме, всё равно был бы виден в
таблице операций.

Что именно подставляет каждый пункт фильтра:

| Пункт фильтра | Условие `WHERE` |
|---|---|
| К1 | `channel='1' AND kassa='k1'` |
| К2 | `channel='1' AND kassa='k2'` |
| Банк | `channel='bank'` |
| Сейф | `channel='safe'` |
| Курьер | `channel='cur'` — **обе** кассы, чтобы старые записи по Курьер 2 не пропали из вида |
| все | без условия по каналу (плюс скрытие банка/сейфа без прав) |

**Что сохраняем из белорусской версии** (в польской этого нет):

- проверку доступа `$_SESSION['svoi'] == 8941` и уровни `$in_level`;
- кнопку «i» — правку статьи и комментария существующего расхода (только владелец);
- удаление связанной пары операций перевода по `link_to`, с записью в журнал через
  `\bb\classes\DohRash::logBeforeDelete()`;
- список `$in_del` — кому доступно удаление;
- показ `dr_id` для Димы (`User::getCurrentUser()->isDima()`);
- меню `.top_menu` и `stile.css`: в польской версии есть хелпер `nav_icons()`, которого в
  белорусском `bb/` нет, поэтому шапку меню оставляем свою.

**Валюта** — BYN (в польской версии переменная `$CUR`).

**Выручка для плитки «сальдо»** считается по методике, зафиксированной в
`app/Http/Controllers/Mcp/CLAUDE.md`: `SUM(r_paid + delivery_paid)` по
`UNION(rent_sub_deals_act, rent_sub_deals_arch)` с фильтром по `acc_date`. Польский вариант с
условием по `r_payment_type` не переносим — там другая методика и другой набор каналов оплаты.

## Архитектура кода

Файл сейчас 1102 строки, из них ~200 — четыре копии одного и того же `switch` по каналам.
Польская версия эту дублирующуюся логику уже свернула в функции; переносим тот же приём:

| Функция | Ответственность |
|---|---|
| `channels_all()` | единый справочник каналов: код → `[текст, channel, kassa, архивный?, только_перевод?, требует_прав?]` |
| `channels_for_form($type1, $user)` | список для формы: фильтрует архивные, сейф вне переводов, банк/сейф без прав |
| `channel_to_office_kassa($code)` | код канала → пара `[channel, kassa]` для записи в БД |
| `channel_sql_filter($code)` | код канала → кусок `WHERE` для фильтра |
| `of_print()` / `kassa_print()` | расшифровка исторических значений в таблице |

Справочник каналов — **единственный** источник правды: и фильтр, и форма, и валидация, и
расшифровка строятся из него. Добавление шестого канала в будущем = одна строка.

## Смежные системы

**MCP API `/finance/entries`** (`FinanceEntriesController`) пишет в ту же таблицу и имеет жёсткий
белый список: `kassa` ∈ {`k1`,`k2`,`bank`,`card`}, `channel` ∈ {номер офиса, `cur`, `bank`}, плюс
правило пары в `channelKassaPairValid()`. Строки с `safe` этот список отклонит.

Решение: расширить белый список и правило пары на `safe`+`safe` в рамках этой же работы — иначе
агент, читающий и правящий кассовую книгу через API, не сможет ни создать, ни исправить операцию
по сейфу. Изменение маленькое и локальное: два массива и одна ветка в `channelKassaPairValid()`.

**Не трогаем:** таблицу `kassas` и `KassaOstatok` (сейф в дневных остатках не участвует —
решение 2 выше), недостроенную подсистему `KassaChannel`/`KassaOperation`, отчёты `reports.php`,
`dohrash2.php`, `rash_analysis.php`.

## Тестирование

Легаси-часть `bb/` тестами не покрыта, PHPUnit её не видит. Проверка — ручная, по чек-листу:

1. Форма: расход по К1 / доход по К2 / перевод К1 → Сейф / перевод Сейф → К1.
2. Перевод создаёт **две** связанные строки (`shift_minus` + `shift_plus`) с обоюдным `link_to`;
   удаление одной удаляет обе.
3. Сейфа нет в списке каналов на вкладках «Расход» и «Доход».
4. Сотрудник не из списка {2,3,5,9} не видит ни Банк, ни Сейф — ни в форме, ни в таблице.
5. Попытка отправить `channel=safe` с `type1=rash` в обход JS отклоняется сервером.
6. Фильтр по каждому из пяти каналов возвращает ожидаемые строки; «все» показывает и архивные.
7. Старые записи по Складу / Победителей / Ложинской / Курьер 2 читаются в таблице с названиями.
8. Итоги: сумма в плитке расходов совпадает с итогом колонки; переводы в итоги не входят.

Для MCP-части — существующие тесты `tests/Feature/Mcp/` должны продолжать проходить, плюс
проверка создания записи с `kassa=safe`.

## Риски

| Риск | Смягчение |
|---|---|
| Ненулевой остаток на архивном канале нельзя будет снять | Снят: заказчик подтвердил нулевые остатки (2026-08-11) |
| `safe` встретится в коде, который ждёт числовой офис (`KassaOstatok`) | Сейф в дневные остатки не попадает по решению 2; запросы `KassaOstatok` фильтруют по конкретному офису, `safe` в них не приходит |
| Полная переверстка ломает привычный сценарий работы | Выкатывать после демонстрации заказчику; логика операций не меняется, меняется только оболочка |
| Расхождение с польской версией со временем | Функции названы так же, как в PL, чтобы правки переносились между проектами |
