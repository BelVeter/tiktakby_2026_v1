# Заявки (demand requests) — редизайн: связь со звонками, статусы, дата выдачи, анти-дубль

**Дата:** 2026-06-05
**Ветка:** `feature/zayavki-redesign`
**Автор обсуждения:** Dmitry + Claude (brainstorming)

---

## 1. Контекст и проблема (по данным прода)

Заявка — это запрос клиента на товар, которого сейчас нет в наличии (`rent_orders.type2='zayavka'`). Используется для обзвона клиентов при поступлении товара и для анализа спроса.

Данные с продакшна (2026-06-05):

- Активных заявок — 37, в архиве (`rent_orders_arch`) — **14 882**.
- **58% заявок без телефона** (`phone=0`): 8 704 из 14 882. Причина: `rent_orders.phone` = `bigint NOT NULL` без дефолта → пустой телефон пишется как `0`, а доска показывает телефон только при `phone > 1`.
- **Почти у каждой заявки в свободном тексте зашита дата** («к 20.06», «с 23 июня», «22 июня»). Отдельного поля под это нет — есть только `validity` (срок действия заявки).
- Дубли: 134 кластера / 213 лишних строк (только среди заявок **с** телефоном и **после** ручной чистки за последний месяц). Проблема воспроизводится постоянно.
- **Связи `zvonki` ↔ `rent_orders` нет.** Кнопка «Оформить заявку» в `zv_ch.php` нажата всего 1 559 раз против 14 882 заявок: заявку создаёт сайт, а оператор работает в звонках и в доску заявок почти не заходит. 1 747 звонков `type1='zayavka'` висят необработанными >7 дней.

### Механизм дублирования

Каждая из точек создания (сайт: страница товара, корзина, модалка заявки) создаёт **две** записи за одну отправку: `zvonki` (уведомление) + `rent_orders` (заявка). Звонок попадает в `zv_ch.php` с кнопкой «Оформить заявку», и оператор, обрабатывая звонок, создаёт **вторую** заявку поверх уже существующей. Защиты нет: `Zvonok::addLitZvonok` имеет `isDublicate()`, а `bron::createZayavka` — нет, и в `rent_orders` нет уникального индекса.

## 2. Цели и не-цели

**Цели:**
1. Связать звонок и заявку (`zvonki.order_id → rent_orders.order_id`), чтобы из звонка была обратная связь и не плодились дубли.
2. Жизненный цикл заявки (статусы) — user-friendly, не блокирующий, выводимый из действий оператора.
3. «Планируемая дата выдачи» как отдельное поле (сортировка/фильтр).
4. Возможность сменить модель в заявке (уговорили на другую).
5. Soft-delete с причиной (физически не удаляем — это уже так, добавляем статус/причину).
6. Анти-дубль: не терять заявку, но подсвечивать «повторная» с ссылкой на существующую.
7. Единый backend-класс для всей логики заявки; единый источник правды в UI.
8. Покрыть тестами.

**Не-цели (YAGNI / отдельно):**
- Активные напоминания/дайджесты по `planned_date` — позже, мелкой доработкой.
- Слияние `rent_orders` и `rent_orders_arch` — НЕ делаем (см. §3).
- Массовый рефакторинг легаси `bb/` (PDO, устранение `$$key` из `$_POST` везде) — НЕ делаем; только новый код пишем правильно (см. §13).
- Отдельная таблица событий/аудита заявок — не нужна для текущих целей.

## 3. Архитектурное решение: act/arch остаётся

`rent_orders` + `rent_orders_arch` — это сквозная hot/cold-конвенция всей базы (11 пар `_act/_arch`), а не дефект. На ней построена MCP-аналитика (методология зафиксирована 2026-05-14, читает воронку через `rent_orders_arch`), а также `reports.php` и страница «Удалённые заявки» `rent_zayavk_arch.php`. Схемы различаются: `rent_orders_arch` = поля `rent_orders` + 3 ведущих (`arch_order_id, arch_time, arch_who`).

**Решение:** таблицы не сливаем.

«Физически не удаляем» уже работает: текущее «удалить» делает `arch_copy()` (INSERT в `rent_orders_arch`), затем `del_br()` (DELETE из активной). Данные сохраняются, есть готовая страница «Удалённые заявки». Нам нужно лишь **записывать причину/статус перед архивацией**.

Терминальные статусы (`rejected`, `spam`) → проставляем `z_status`+причину на активной строке → штатный `arch_copy → del`. Активная доска показывает только `new`/`in_work`. Новые колонки добавляем **в обе** таблицы.

## 4. Изменения схемы (миграции Laravel, аддитивные)

### `rent_orders` и `rent_orders_arch` (обе)
- `z_status` `VARCHAR(20) NOT NULL DEFAULT 'new'` — `new | in_work | done | rejected | spam | deleted`. Значимо только при `type2='zayavka'`. Бронь не трогаем (у неё свой `status`). Смысл терминальных: `done` = ушла в бронь; `rejected` = клиент отказался (с причиной); `spam` = мусор/тест; `deleted` = оператор удалил ошибочную/дубль вручную.
- `z_reject_reason` `VARCHAR(40) NULL` — `out_of_stock | changed_mind | too_expensive | found_elsewhere | other`.
- `planned_date` `DATE NULL` — планируемая дата выдачи.

### `rent_orders` — телефон НЕ трогаем (тип колонки оставляем)
Исследование показало: «58% без телефона» — это **мёртвая легаси-данные 2016–2019** (старый код вставки заявки не имел поля phone вообще; 100% phone=0 в те годы). С ~2020 телефон сохраняется, текущий phone=0 — 1–2% и это реальные край-кейсы (клиент оставил контакт в тексте: Viber/Telegram). Жёстко требовать телефон на уровне БД нельзя (потеряем такие лиды).

- **Тип колонки `phone` не меняем** (она участвует в позиционных INSERT — см. §4a, лишний риск).
- В UI **подсвечиваем заявку без телефона** («⚠ нет телефона — контакт в комментарии»), чтобы оператор нашёл альт-контакт.
- Дедуп по телефону работает только при `phone > 1` (0/пустой не матчим).

### `zvonki`
- `order_id` `INT NULL DEFAULT NULL` — ссылка на `rent_orders.order_id` (заявка, к которой относится звонок). Много звонков могут ссылаться на одну заявку (повторные).

### Индексы (под дедуп и доску)
- `rent_orders (model_id, phone)` — поиск дублей.
- `rent_orders (type2, z_status)` — выборка активной доски.
- `zvonki (order_id)` — связь.

### Одноразовый бэкафилл (в той же миграции или отдельном скрипте)
- `UPDATE rent_orders SET z_status='new' WHERE type2='zayavka' AND (info2 IS NULL OR info2='')`; остальные активные заявки → `in_work`. (Сейчас «новизна» определяется пустотой `info2` — переносим в статус.)

## 4a. ОБЯЗАТЕЛЬНО до добавления колонок: позиционные INSERT → явные колонки

`rent_orders` — общая таблица для броней и заявок (`type2 IN bron/deliv/remont/out/zayavka/stirka/sell`). В живом коде везде **позиционные** `INSERT INTO rent_orders VALUES (29 значений)`. Сейчас в таблице ровно 29 колонок. Добавление любых колонок без правки этих INSERT → MySQL «Column count doesn't match value count» → **ломается создание ВСЕХ типов записей (включая брони) на сайте и в админке.**

Поэтому **до** добавления колонок переводим живые позиционные запросы на явный список колонок:

| Файл | Что | Тип записей |
|---|---|---|
| [bb/classes/bron.php:520](../../../bb/classes/bron.php) `insert()` | `INSERT INTO rent_orders (…) VALUES (…)` | все брони + заявки |
| [bb/classes/bron.php:805](../../../bb/classes/bron.php) `arch_copy()` | `INSERT INTO rent_orders_arch (…) SELECT …` | архивация/удаление |
| [includes/l_3_br.php:343/416/508](../../../includes/l_3_br.php) | 3× `INSERT INTO rent_orders (…) VALUES (…)` | брони + заявки с сайта |

После этого добавление колонок безопасно (новые получают `DEFAULT`), брони работают как прежде, и код защищён от поломок при любых будущих добавлениях колонок.

**Мёртвые** позиционные INSERT не трогаем (нигде не подключаются, подтверждено): `bb/l_3_br.php`, `bb/classes/old_bron.php`, `bb/bron/rent_orders.php`. `bb/bron.php` (глобальный `class bron`, без namespace) — проверить на этапе реализации, что не используется; если да — тоже не трогаем.

Регрессия проверяется тестом: создать `bron`/`deliv`/`remont`, заархивировать — после конвертации и миграции всё работает.

## 5. Единый backend-класс `bb\classes\Zayavka`

Вся логика заявки — в одном классе (namespace `bb\classes`, который уже импортируют и легаси `bb/`-страницы, и Laravel-контроллеры). Параметризованные запросы (mysqli prepared statements), без `$$key`-присваиваний из `$_POST`.

Публичный API (черновик):

```
Zayavka::create(array $data, string $source): CreateResult
    // $source: 'web_product' | 'web_cart' | 'web_modal' | 'crm'
    // дедуп-осведомлённый; при дубле — связывает звонок, не плодит строку
    // возвращает { order_id, isDuplicate, existing: Zayavka|null, zvonokId }

Zayavka::load(int $orderId): Zayavka
Zayavka::findActiveDuplicate(int $modelId, ?int $phone): ?Zayavka   // active + arch за N мес.
$z->update(array $fields): void          // optimistic-lock по ch_time; история в info2
$z->changeModel(int $newModelId): void   // меняет model_id + cat_id, лог в info2
$z->setStatus(string $status, ?string $reason = null): void  // терминальные → arch
$z->softDelete(?string $reason = null): void   // = setStatus('deleted'); «Отказ» вызывает setStatus('rejected', reason)
$z->linkZvonok(int $zvId): void
$z->toBron(...): void                    // обёртка над существующей z_to_br (done)
```

`bron::createZayavka()` становится тонкой обёрткой над `Zayavka::create()` — старые вызовы не ломаются. Существующий optimistic-lock (`ch_time` / `last_ch_time`) сохраняем и переиспользуем в попапе.

## 6. Анти-дубль и связывание

`Zayavka::create()` ищет существующую заявку по `model_id` + `phone` (только при `phone` валиден) сначала в активных, затем в архиве за последние **6 месяцев** (конфигурируемо).

- **С сайта, дубль найден:** новую строку-заявку не создаём. Создаём звонок-уведомление, **связываем его с существующей заявкой** (`zvonki.order_id`), помечаем «повторная — в базе уже есть заявка (актуальная / удалённая от ДД.ММ)». Оператор видит это в звонках.
- **С сайта, дубля нет:** создаём заявку + звонок, связываем их.
- **Оператор создаёт через CRM, дубль найден:** показываем предупреждение с карточкой существующей заявки и кнопками «Открыть существующую» / «Всё равно создать».
- **Оператор, дубля нет:** обычное создание.

Заявка не теряется ни в одном сценарии — звонок-уведомление создаётся всегда.

## 7. Жизненный цикл (статусы) — не блокирующий

Статус выводится из действий, которые оператор и так делает; явный клик нужен только для отказа/спама.

| Статус | Как ставится | Клики |
|---|---|---|
| `new` | автоматически при создании | 0 |
| `in_work` | автоматически при первом действии (коммент / «недозвон» / сохранение в попапе), если был `new` | 0 |
| `done` | автоматически при «самовывоз» (заявка → бронь) | 0 (кнопка уже есть) |
| `rejected` | кнопка «Отказ» → чипсы причины (необязательно) → arch | 1 |
| `spam` | кнопка «Спам» → arch | 1 |

«Счастливый путь» (заявка → дозвон → бронь) не требует ни одного нового клика.

- Фильтр/сортировка по статусу и планируемой дате.
- Выборка доски: `type2='zayavka' AND z_status IN ('new','in_work')`.

## 13. Конверсия заявки в бронь — учёт для аналитики (решение)

При «самовывоз» текущий `z_to_br()` превращает ту же строку в бронь (`type2='bron'`), `order_id` сохраняется. Отдельную arch-копию заявки на конверсии **не создаём** (иначе раздуем счётчики лидов в MCP-воронке, которая считает строки `rent_orders_arch`, и придётся править MCP + LegacyParityTest — лишняя кровь).

«Выиграно/проиграно» для анализа спроса определяем так:
- **lost / spam** — arch-строки заявок с `z_status IN ('rejected','spam')` (они и так уходят в arch при удалении — это аддитивная колонка, MCP не меняется).
- **won** — по связанному звонку (`zvonki.type1='zayavka_done'`) и по сохранённому `order_id` (строка продолжает жить как бронь/сделка).
- **pending / expired** — активные или arch с `z_status IN ('new','in_work')` (и `validity` в прошлом = просрочено).

Если позже понадобится точная воронка won/lost — добавим лёгкую таблицу событий (отдельная задача).

## 14. Безопасные фиксы «не сильно большой кровью» (opt-in)

Найдено по ходу; предлагаю, решение за тобой. Все — низкого риска и в рамках затрагиваемого кода:

1. **Явные колонки в INSERT** (§4a) — обязательная и самая ценная правка: устраняет хрупкость позиционных запросов раз и навсегда. Подсветка заявок без телефона в UI (§4) вместо смены типа колонки.
2. **Prepared statements в новом коде** (класс `Zayavka` + `zayavka_api.php`): без строковой интерполяции SQL и без `$$key` из `$_POST`. Ноль крови — просто пишем новый код правильно.
3. **Точечный `update()`**: новый класс обновляет только изменённые поля, а не переписывает все колонки (включая `cr_time`/`cr_who_id`), как делает легаси `bron::update()`. Снижает риск затереть метаданные создания.
4. **Индексы под дедуп/доску** (уже в §4) — попутно ускоряет существующие выборки заявок.

Чего **не** делаю (большая кровь, вне скоупа): перевод всего `bb/` на PDO, устранение `$$key` во всех легаси-страницах, слияние act/arch.

## 15. План тестирования

**PHPUnit (Feature, на тестовой БД):**
- `Zayavka::create()` — создание без дубля; дубль с сайта (не плодит, связывает звонок, флаг «повторная»); дубль из CRM (возвращает existing); телефон пустой → `NULL`, дедуп его игнорирует.
- Статусы: авто `new→in_work` при первом действии; `setStatus('rejected', reason)` → строка в arch со статусом+причиной, из активной убрана; `spam` аналогично; happy-path до `done`.
- `changeModel()` — меняет `model_id`+`cat_id`, пишет историю, сохраняет `order_id`.
- Optimistic-lock: параллельное редактирование (`ch_time` рассинхрон) → отказ.
- `softDelete()` — копия в arch есть, физического удаления нет.
- Связь: `zvonki.order_id` проставляется; «Редактировать заявку» грузит правильную заявку.
- **Регрессия броней (критично):** после конвертации позиционных INSERT (§4a) и миграции — создать `bron`, `deliv`, `remont`, заархивировать (`arch_copy`), убедиться что записи создаются и корректно копируются в `rent_orders_arch`. Это страховка, что общая таблица не сломана.
- Регрессия: существующие MCP-тесты (`MarketingTest`, `MetaTest`, `LegacyParityTest`) проходят без изменений (колонки аддитивные).

**Ручная проверка (после деплоя на стейдж/прод по согласованию):**
- Создание заявки с сайта (нет в наличии) → одна заявка + связанный звонок.
- Повтор той же модели с тем же телефоном → «повторная», без новой строки.
- Редактирование из попапа на звонках и с доски — один и тот же результат.
- Сортировка/фильтр по планируемой дате.

## 17. Откат и риски

- **Главный риск — позиционные INSERT (§4a).** Добавление колонок без конвертации сломает создание всех записей в `rent_orders` (включая брони). Митигация: сначала конвертация в явные колонки, затем миграция; регрессионный тест броней.
- Миграция аддитивная и обратимая (`down()` дропает колонки/индексы). Тип колонки `phone` не меняем — обратной несовместимости нет.
- Риск двойного счёта в MCP исключён решением §13 (не создаём новых arch-строк на конверсии).
- Порядок деплоя: конвертация INSERT (§4a) + миграция колонок выкатываются **вместе**, одним деплоем.
