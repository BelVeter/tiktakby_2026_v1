# Трекинг использования CRM (bb/) — спецификация

**Дата:** 03.09.2026
**Ветка:** `feature/crm-usage-tracking` (создать свежую от `origin/main`)

---

## Задача

Владелец хочет видеть, кто из сотрудников на какие страницы легаси-админки `bb/`
заходит и как часто, а какие страницы не открывает никто. Цель — поровну и «активность
сотрудников», и «неиспользуемые страницы» (кандидаты на чистку легаси).

Сегодня в `bb/` уже есть `logpass_track` + `staf_track.php` — учёт входов/выходов в
систему (кто залогинился, когда, из какого офиса). Это не покрывает вопрос «какие именно
страницы открывает залогиненный сотрудник» — такого учёта нет.

`bb/` — гибридная легаси-кодовая база без единой точки входа: из ~176 `.php`-файлов
верхнего уровня только 13 подключают `auth_guard.php` и ещё 13 — `bb_nav.php` (который
сам тянет `auth_guard.php`). Самые ходовые страницы (`deals.php`, `tovar.php`,
`kr_baza_new.php`, `item_ch.php` и т.д.) делают свою инлайн-проверку `$_SESSION['svoi']`
и не проходят ни через один общий файл. Правка каждой страницы вручную — ~170 точек
правки, легко забыть при добавлении новой страницы в будущем.

---

## Решение

### Точка перехвата: `auto_prepend_file` через `bb/.htaccess`

Один скрипт подключается PHP-движком перед выполнением любого `.php`-файла в `bb/`, вне
зависимости от того, что подключает сама страница. Правки в существующих файлах страниц
не требуются.

`bb/.htaccess` уже содержит `php_flag display_errors Off` — директивы `.htaccess`-уровня
в этом хостинге применяются, значит и `php_value auto_prepend_file` будет работать тем же
механизмом.

```
php_value auto_prepend_file /home/USER/public_html/bb/classes/PageVisitTracker.php
```

(точный абсолютный путь — по факту на проде; локально в Docker — эквивалент через
volume-путь).

**Риск**: если PHP на хостинге работает через FPM, `.htaccess`-директива
`auto_prepend_file` иногда не применяется (в отличие от `.user.ini`). Проверяется
локально в Docker до мержа. Если после деплоя на проде не сработает — запасной план без
правки кода: `bb/.user.ini` с той же директивой.

Отклонённые варианты:
- **Встроить в `auth_guard.php`/`bb_nav.php`** — покрывает меньшинство трафика (см.
  выше), самые важные страницы мимо.
- **Ручная правка каждой из ~170 страниц** — избыточный объём правок легаси ради разовой
  задачи, риск забыть про новую страницу в будущем.

### Данные: таблица `bb_page_visits`

Laravel-миграция (миграции на проде снова рабочие, см. `docs/db_notes.md` п.7):

| колонка       | тип                      | примечание                          |
|---------------|--------------------------|--------------------------------------|
| `id`          | PK                       |                                      |
| `user_id`     | int, индекс              | из `$_SESSION['user_id']`           |
| `page`        | varchar(100), индекс     | basename файла, без query-строки    |
| `visited_at`  | datetime, индекс         |                                      |

Составной индекс `(user_id, page, visited_at)` под агрегацию отчёта.

Без IP и без query-строки — не требуется для «кто/что/как часто», а хранить лишнее
(потенциально с ПДн клиентов в URL) незачем.

### Логика трекера (`bb/classes/PageVisitTracker.php`)

1. Если `session_status() === PHP_SESSION_NONE` — `session_start()` (как в
   `auth_guard.php`).
2. Если `$_SESSION['user_id']` не установлен — выход, писать нечего (не залогинен —
   например, ещё на экране логина).
3. Если запрос технический — выход, без записи:
   - заголовок `X-Requested-With: XMLHttpRequest` (страхует от будущих ajax-скриптов
     автоматически, не только от уже существующих);
   - имя файла начинается на `ajax_`, оканчивается на `_api.php` или `_badge.php`.
4. Иначе — `INSERT` строки `(user_id, page, visited_at=NOW())` через
   `\bb\Db::getInstance()->getConnection()` (тот же паттерн доступа к БД, что и везде в
   `bb/`), обёрнутый в try/catch — сбой логирования не должен ронять страницу, которую
   открывает сотрудник.

И GET, и POST считаются заходом — отправка формы на странице тоже означает, что
страницей пользуются.

Правило «это техническая страница или нет» (шаг 3) реализуется одной shared-функцией,
которую использует и трекер (что не логировать), и отчёт (что не считать «страницей» при
поиске неиспользуемых, шаг ниже).

### Страница отчёта: `bb/page_track.php`

По аналогии с существующей `staf_track.php` (общий менюшный `<a href="/bb/index.php">`,
форма-фильтр, `<table>`).

**Доступ**: `\bb\models\User::getCurrentUser()->isDima()` (метод уже существует,
`id_user=3`) — иначе `die()` с тем же экраном авторизации, что у остальных защищённых
страниц. Только владелец, не общий уровень admin/owner.

**Фильтр**: период `от`—`до` (как в `staf_track.php`), по умолчанию последние 30 дней.

**Таблица 1 — по сотрудникам**: сотрудник (имя из `User::getUsers()`), кол-во заходов за
период, кол-во уникальных страниц, дата последней активности. Сортировка по кол-ву
заходов по убыванию.

**Таблица 2 — по страницам**: список реальных страниц `bb/*.php` минус те же технические
паттерны (шаг 3 трекера) минус явные классы/модели, к которым нет прямого URL (`Db.php`,
`Base.php`, `models/*`, `classes/*` и т.п. — они физически не в `bb/*.php` верхнего
уровня, так что скан по маске уже их не заденет). Для каждой страницы — кол-во заходов за
период, кол-во уникальных сотрудников, дата последнего захода. Сортировка по кол-ву
заходов по возрастанию — сначала то, чем не пользуются вообще (0) или почти не
пользуются.

Без сводной матрицы «сотрудник × страница» в первой версии — два простых списка
покрывают и «кто чем занят», и «что не трогают»; матрица — возможное расширение позже,
если понадобится более тонкий разрез.

## Осознанные компромиссы

- **Идентификатор страницы — просто basename файла**, без учёта query-параметров
  (`item_ch.php?id=5` и `item_ch.php?id=9` — одна и та же «страница» для целей отчёта).
  Вопрос был не про конкретные записи, а про то, какие экраны вообще используются.
- **Нет дедупликации/троттлинга повторных заходов** — каждый некэшируемый запрос
  считается отдельной строкой. Шум от частого рефреша одной и той же страницы одним
  сотрудником agregируется в отчёте через «кол-во заходов» — это осознанно отражает
  реальную интенсивность использования, а не искусственно сглаживается.
- **Нет retention/автоочистки лога** — объём (сотрудники × реальные страницы, без ajax)
  на масштабах этой команды не потребует чистки в обозримом будущем; если понадобится —
  добавляется отдельной задачей.
- **Доступ к отчёту — только `isDima()`**, не общий owner-уровень (`isOwner()`, id 2,3,5)
  — по прямому запросу владельца.

## Не в объёме

- Сводная матрица «сотрудник × страница».
- Ручное тестирование в браузере — сделаю через `docker compose` локально (визит на
  несколько страниц bb/, проверка что строки появляются/не появляются в
  `bb_page_visits`, проверка отчёта); реального стенда с несколькими живыми
  учётками сотрудников для теста нет, так что многопользовательский сценарий проверяется
  только на уровне SQL/логики, не UI с разных сессий.
- Автоматических тестов Laravel `TestCase` для самих файлов `bb/` не будет — они не
  роутятся через Laravel-ядро (см. `AGENTS.md`), Laravel-фичатесты не могут дойти до
  этих URL. Проверка — миграция (структура таблицы) через `php artisan migrate` в Docker
  + ручной прогон трекера.

---

## Тесты

- `php artisan migrate` в Docker — таблица `bb_page_visits` создаётся с ожидаемыми
  индексами.
- Ручной прогон в Docker: зайти на несколько реальных страниц (`deals.php`,
  `tovar.php`) под тестовым логином — строки появляются; дёрнуть `ajax_*`/`*_api.php`
  напрямую и через XHR-заголовок — строки не появляются; зайти без логина (на экран
  логина) — строк нет.
- Открыть `page_track.php` под `isDima()`-пользователем — обе таблицы рендерятся,
  фильтр по датам работает; под другим пользователем — `die()` с экраном авторизации.

## Порядок работ

Работа идёт локально на свежей ветке `feature/crm-usage-tracking` от `origin/main` (прод
не трогаем, см. `docs/prod_pending.md`).

1. Миграция `bb_page_visits`.
2. `bb/classes/PageVisitTracker.php` — shared-функция «техническая страница?» + логика
   записи захода.
3. `bb/.htaccess` — добавить `php_value auto_prepend_file` с путём к трекеру.
4. `bb/page_track.php` — страница отчёта (фильтр по датам, две таблицы, гейт
   `isDima()`).
5. Ручная проверка в Docker (см. «Тесты» выше).
6. Обновить `docs/prod_pending.md` — не забыть проверить после деплоя, что
   `auto_prepend_file` реально сработал на проде (риск FPM, см. выше); если нет —
   переключить на `bb/.user.ini`.
