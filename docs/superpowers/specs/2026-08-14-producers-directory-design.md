# Справочник производителей — спецификация

**Дата:** 14.08.2026
**Ветка:** `feature/producers-directory`
**Продолжает:** `docs/superpowers/plans/2026-07-27-tovar-new-mod-hardening.md` (Фаза 7)

---

## Задача

На странице новой модели производитель вводится свободным текстом. Любая опечатка
создаёт **новый бренд** со всеми последствиями, потому что логотип бренда цепляется к
строке **точным совпадением**: `Model::getModelIdsArrayByProducer()` делает
`WHERE producer='...'`, а на нём стоят `ModelWeb::loadLastProducerLogo()` и
`updateLogoUrlForAll()`.

Одна лишняя буква даёт: модели, отрезанные от логотипа своего же бренда; вторую карточку
на главной; второй адрес `/ru/producer?producer=...`.

Цель — закрыть приток новых написаний и дать бренду одно место, где он заведён.

---

## Что показали данные

Замеры сняты с локального снимка базы, на котором **уже прогнана** нормализация из ветки
`fix/catalog-normalize-producers` (на прод она не влита — см. `docs/prod_pending.md`).

| Показатель | Значение |
|---|---|
| Производителей | 326 |
| Моделей | 1668 |
| Брендов ровно с одной моделью | 184 (56 %) |
| Веб-страниц моделей | 844 |
| Из них с логотипом | 392 |
| Разных файлов логотипов | 136 |
| Брендов, у которых копии логотипа разъехались | 3 |
| Брендов без логотипа (не видны на главной) | 186 из 326 |

Логотип хранится **на веб-странице каждой модели** (`rent_model_web.logo`), то есть 392
строки держат 136 файлов — примерно по три копии на файл. Сущности «бренд» в базе нет.
Главная восстанавливает список брендов из этих копий:
`SELECT producer, MAX(logo) ... GROUP BY producer WHERE logo != ''`.

Прямое следствие копий — модель 1053 «Хипсит» бренда `Baby Mamy` показывает логотип
**`logo_pognae.webp`**, то есть чужой бренд на карточке товара.

### Где рождаются новые написания

Запись в `producer` есть только в трёх живых местах (`bb/tovar_new_mod.php`,
`bb/tovar_new.php`, архивация в `bb/classes/tovar.php`). Из них **свободный ввод — ровно
один**: поле производителя на странице новой модели. На странице товара производитель уже
выбирается каскадом из существующих, архивация просто копирует готовое значение.

Значит шлюз нужен один. При этом **читают** строку 52 файла — поэтому переход на
`producer_id` с внешним ключом несоразмерен риску и в этой работе не делается.

### Подозрительные написания, оставшиеся после июльской чистки

| Похожесть | Пара | Вердикт |
|---|---|---|
| 1.00 | `Kinder Kraft` (1 модель, 0 единиц, без лого) / `Kinderkraft` (2 модели, 2 единицы, лого есть) | дубль → `Kinderkraft` |
| 1.00 | `Baby Mamy` (2 модели) / `Babymamy` (1 модель) | дубль → `Babymamy` |
| 1.00 | `Maxi Cosi` (5 моделей, 2 ед.) / `Maxi-Cosi` (11 моделей, 15 ед.) | дубль → `Maxi-Cosi` |
| 0.75 | `Medel` / `Medela` | **разные бренды**, не сливать |
| 0.40 | `аксессуар` (21) / `акссесуар` (9) | дубль → `аксессуар` |

Коллация `utf8mb3_general_ci` склеивает регистр и хвостовой пробел, но **не** склеивает
внутренний пробел и дефис — поэтому первые три пары в базе разъехались по-настоящему.

### Поле используется не только под бренд

В карнавальных категориях (`tovar_rent_cat.cat_type=1`) в `producer` лежат вперемешку
бренды (`Батик` — 188 моделей, `Rabie's` — 32), страны (`РБ` — 32, `РФ` — 6, `Польша` — 2),
типы вещей (`аксессуар` — 21, `вечернее` — 5) и просто `-` (13). Разбирать это в текущей
работе не будем — достаточно убрать такие значения из подсказок.

## Решение

### Таблица `producers`

| Колонка | Назначение |
|---|---|
| `producer_id` | PK |
| `name` | каноничное написание, UNIQUE |
| `name_norm` | нормализованная форма, индекс — по ней работает детектор дублей |
| `logo` | путь к файлу; **одна строка на бренд** |
| `comment` | заметка вроде «не путать с Medel» |
| `is_active` | убрать из подсказок, не трогая данные |
| `cr_time`, `cr_user_id`, `ch_time`, `ch_user_id` | кто завёл и менял |

`tovar_rent.producer` остаётся строкой. Справочник — источник для **записи** и для витрин;
52 читающих места не переписываются.

### Детектор дублей: две метрики вместо одной

Триграммный Jaccard (`bb/classes/Similarity.php`, уже написан) разваливается на коротких
словах — в пятибуквенном слове около пяти триграмм, и одна изменённая буква убивает три:

| Пара | Jaccard | Поймал? |
|---|---|---|
| `Kinder Kraft` / `Kinderkraft` | 1.00 | да |
| `аксессуар` / `акссесуар` | 0.40 | **нет** |
| `Chicco` / `Chico` | 0.40 | **нет** |
| `Батик` / `Ботик` | 0.20 | **нет** |

Это ровно тот тип опечатки, ради которого всё затевается. Поэтому к триграммам добавляется
**расстояние Левенштейна по нормализованной форме**, UTF-8-безопасное: штатный
`levenshtein()` работает побайтово и на кириллице считает неверно, поэтому строки бьются
через `preg_split('//u')`.

Предупреждаем, если сработала **любая** из метрик. Совпадение нормализованных форм — не
предупреждение, а запрет.

### Главный принцип: детектор предупреждает, решает человек

`Medel` и `Medela` — разные реальные бренды, а по расстоянию Левенштейна они 0.83.
Автослияние здесь испортило бы данные. Поэтому машина показывает пару и свои аргументы
(сколько моделей, сколько живых единиц, какие логотипы), а сводит человек. Решение «это
разные бренды» запоминается в `comment`, чтобы пара не всплывала снова.

По той же причине засев справочника идёт **как есть**, без автослияния.

### Живой поиск — два разных

**Страница новой модели (`bb/tovar_new_mod.php`)** — бренд здесь *назначается*.
Источник: справочник, только активные. Порядок: сначала бренды, уже встречающиеся в
выбранной категории (категория к этому моменту выбрана виджетом из предыдущей работы),
затем остальные по алфавиту; если категория ещё не выбрана — просто алфавит. Рядом —
кнопка «+ создать», после выбора — «редактировать».

Скрытые (`is_active=0`) в подсказках не показываются, но находятся при вводе точного
названия и помечаются «скрыт» — иначе выключенный бренд стало бы невозможно включить
обратно, не заводя отдельную страницу управления.

**Страница нового товара (`bb/tovar_new.php`)** — бренд здесь *сужает каскад* до
существующей модели. Источник: `SELECT DISTINCT producer FROM tovar_rent WHERE
tovar_rent_cat_id=...`, как сейчас делает `bb/cat_ch_new.php`. Не справочник — иначе можно
выбрать бренд, у которого в этой категории нет ни одной модели, и упереться в пустой
список моделей. Кнопок создания и редактирования здесь нет. Виджет пишет в скрытое поле с
тем же `id`/`name` (`producer_select_old`), чтобы существующий каскад
`cat_ch()` / `prod_ch()` / `model_ch()` продолжал работать без правок.

### Попап создания

Поля: название, комментарий. Логотип не спрашиваем — он заливается на странице веб-модели.

При вводе идёт живая проверка: точный дубль — запрет; похожие — предупреждение со списком
и кнопкой «всё равно создать». Права: уровни 0, 5, 7 — как создание категории.

### Попап редактирования

Правится название, комментарий, `is_active`. Логотип — нет.

Три защиты:

1. **Предпросмотр.** До подтверждения показываем масштаб: «затронет 11 моделей,
   15 единиц, 4 архивных записи».
2. **Одна транзакция.** Справочник, `tovar_rent`, `tovar_rent_items` и
   `tovar_rent_items_arch` меняются вместе либо не меняются вовсе.
3. **Переименование в уже существующее имя запрещено.** Это слияние, а не переименование,
   и оно необратимо. Сообщаем сотруднику, что бренд уже есть; слияния делаются миграцией
   через PR. Так попап остаётся простым, а опасная операция — под ревью.

Права: уровни 5 и 7, как архивация категорий. Операция трогает три таблицы.

После записи сбрасывается кэш `all_producers_tov_exists`.

### Логотип

**Вводится** там же, где сейчас — в редакторе веб-страницы модели (`bb/model_web.php`).
Для сотрудника не меняется ничего: то же поле, то же поведение «залил на одной модели —
применилось ко всему бренду».

**Сохраняется** в `producers.logo` — одна строка вместо рассылки пути по всем страницам
бренда. `ModelWeb::updateLogoUrlForAll()` заменяется на запись в справочник.

Справочник засеян из всех существующих значений `producer`, поэтому бренд модели в нём
есть всегда. Но если по строке он всё же не нашёлся (значение появилось в обход шлюза),
логотип пишется только в старую `rent_model_web.logo` — как раньше. Молча терять заливку
нельзя.

**Читается**: L3 берёт логотип из справочника по строке `producer` модели, при пустом
значении падает на старую `rent_model_web.logo`. Главная берёт бренды из справочника,
сохраняя нынешнее условие «есть живые товары».

Колонка `rent_model_web.logo` остаётся на месте как запасной путь — день переключения
ничего не ломает.

Видимое следствие: у трёх брендов разъехавшиеся копии схлопнутся в одну, и `Baby Mamy`
перестанет показывать чужой `logo_pognae.webp`. Это починка, но она видна на сайте.

## Осознанные компромиссы

**Нет `producer_id` с внешним ключом.** Строку читают 52 файла; переписывать их ради
чистоты схемы несоразмерно риску. Плата: переименование бренда — это массовый `UPDATE` по
трём таблицам, а не правка одной строки.

**Нет таблицы псевдонимов и 301 для лендинга.** Владелец решил, что лендинг
`/ru/producer?producer=...` сейчас не целевой. Плата: после переименования старый адрес
отдаёт пустую страницу с кодом 200 и `noindex` (`SearchController::producerFilter()` при
нулевом результате ставит `robots: noindex,follow`), а не 301. Хардкод `PRODUCER_RENAMED`
из июльской ветки остаётся как есть. Вернуться к этому — когда лендинг станет целью.

**Нет страницы управления брендами.** Создание живёт в попапе на странице модели, логотип —
на странице веб-модели, переименование — в попапе, слияние — в миграции. На отдельную
страницу не остаётся функций, которые бы её окупали.

**Нет `url_key`.** Понадобится только вместе с лендингом; заводить колонку впрок не будем.

## Не в объёме

- SEO-тексты и адреса лендингов производителей.
- Разбор карнавальной свалки в `producer` (`РБ`, `РФ`, `Польша`, `вечернее`, `-`).
  Содержательный разбор — в бэклог; здесь такие значения только гасятся через `is_active`
  в миграции засева, по списку, который владелец утверждает заранее. Через попап их не
  выключают: сотрудник не должен решать, что считать брендом.
- `bb/model_clean.php` — написан на `mysql_*`, которого в PHP 7.4 нет, страница падает с
  фатальной ошибкой, ссылок на неё ниоткуда нет. Мёртвая, в бэклог на удаление.
- Замена `<select>` моделей (около 1800 позиций) на живой поиск — следующий шаг.

## Тесты

- `Similarity`: расстояние Левенштейна на кириллице; что `аксессуар`/`акссесуар`,
  `Chicco`/`Chico`, `Батик`/`Ботик` попадают в предупреждение; что `Medel`/`Medela`
  попадает в предупреждение, но **не** в запрет.
- Засев справочника: в справочнике оказывается ровно столько записей, сколько различных
  значений `producer` в базе (число зависит от среды — на локальном снимке 326, на проде
  до влития июльской чистки больше); логотип берётся из `MAX(logo)` по моделям бренда;
  повторный прогон ничего не дублирует.
- Переименование: счётчики строк по трём таблицам совпадают с предпросмотром; откат
  транзакции при ошибке; запрет переименования в существующее имя.
- Логотип: чтение из справочника, фолбэк на `rent_model_web.logo` при пустом значении.
- Права: уровень без доступа не может создать и переименовать.

## Порядок работ

Работа идёт **локально**, прод не трогаем. Ветка `feature/producers-directory` стоит на
`feature/tovar-new-mod-category-picker`, потому что опирается на `LivePicker` и
`Similarity` из неё.

Локально:

1. Левенштейн в `Similarity` + тесты.
2. Миграция: таблица `producers`, засев из существующих значений, логотипы из `MAX(logo)`,
   гашение утверждённого списка не-брендов.
3. AJAX-эндпоинты подсказок, создания и переименования.
4. Живой поиск и попапы на странице новой модели.
5. Живой поиск на странице нового товара (каскад сохраняется).
6. Логотип: запись в справочник, чтение на L3 и главной с фолбэком.

Перед деплоем (порядок влития веток, бэкапы, пересборка отчёта по дублям **на прод-данных**
и утверждение списка слияний владельцем) — в `docs/prod_pending.md`. Отчёт по локальным
данным для слияния не годится: на проде июльская нормализация ещё не применена.
