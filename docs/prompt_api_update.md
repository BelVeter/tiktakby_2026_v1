# Промпт для доработки MCP API tiktak.by: Оптимизация получения аналитики звонков

**Контекст проблемы:**
В текущей реализации API для получения списка звонков используется эндпоинт `GET /calls/recordings`. Он возвращает легковесный список из 100 звонков с базовой информацией (`uuid`, `call_date`, `ai_status`, `ai_business_note` и т.д.).
Однако, чтобы получить результаты ИИ-анализа (оценку тональности клиента `client_sentiment`, тональность оператора `consultant_sentiment` и краткое резюме `ai_summary`), приходится делать отдельные N запросов к `GET /calls/recordings/{uuid}/analysis` в цикле. 

При попытке выгрузить аналитику даже для одной страницы из 100 звонков, мы упираемся в лимиты сервера (ошибка `429 Too Many Requests`), так как сервер не выдерживает 100 последовательных запросов за короткое время. Это делает невозможным массовый анализ настроений клиентов.

**Задача для ИИ-агента бэкенда:**
Необходимо доработать MCP API, чтобы решить проблему N+1 запросов и дать возможность массово выгружать результаты анализа звонков.

**Предлагаемые пути решения (на выбор):**

1. **Вариант А (Предпочтительный): Обогатить текущий метод `GET /calls/recordings`.**
   Добавьте поля `client_sentiment`, `consultant_sentiment` и `ai_summary` (а также `ai_result` и `ai_result_detail`) прямо в ответ списочного метода `GET /calls/recordings`. Само полотно текста (`transcript`) можно туда не включать, чтобы не раздувать payload (оставив его только в детальном методе), но метаданные анализа должны быть в списке.

2. **Вариант Б: Создать новый bulk-эндпоинт.**
   Например, `GET /calls/recordings/analysis/bulk`, который принимает параметры пагинации (`per_page`, `page`, `from`, `to`) и возвращает сразу массив аналитики для запрошенного периода/страницы. 

3. **Вариант В: Передача массива UUID.**
   Сделать возможным POST-запрос на `POST /calls/recordings/analysis/batch` с телом `{"uuids": ["uuid1", "uuid2", ...]}` для получения аналитики пачкой по нужным ID.

**Требования к выполнению:**
1. Выбрать оптимальный вариант и внести изменения в соответствующий контроллер API.
2. Обновить спецификацию OpenAPI (`/openapi.json`), добавив новые поля в схему ответа или описав новый метод.
3. Убедиться, что доработка не ломает существующий контракт для `GET /calls/recordings/{uuid}/analysis`.
4. Обновить документацию в `docs/mcp_server.md` или `docs/mcp_api_migration_2026-05-14.md` при необходимости.
