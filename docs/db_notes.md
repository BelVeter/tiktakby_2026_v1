# DB Notes & Findings (rent_orders / zvonki / заявки)

> Консолидированные находки по архитектуре заявок и особенностям БД. **Читать перед правками `rent_orders`, `rent_orders_arch`, `zvonki` и всего, что связано с заявками/бронями.** Накоплено в ходе редизайна заявок (2026-06-05), см. спеку [docs/superpowers/specs/2026-06-05-zayavki-redesign-design.md](superpowers/specs/2026-06-05-zayavki-redesign-design.md).

## ⚠️ Главные ловушки БД (gotchas)

1. **Позиционные `INSERT ... VALUES` повсюду в легаси.** Многие легаси-запросы пишут `INSERT INTO rent_orders VALUES ('', ...)` без списка колонок. **Добавление любой колонки в такую таблицу ломает ВСЕ такие INSERT** («Column count doesn't match value count»). Перед `ALTER TABLE ... ADD COLUMN` обязательно: (а) найти все позиционные вставки в эту таблицу (`grep -rniE "INSERT INTO <table> VALUES"`), (б) перевести живые на явный список колонок. Счётчики колонок: `rent_orders` = 29, `rent_orders_arch` = 32 (3 ведущих arch-поля), `zvonki` = 14.

2. **act/arch — сквозная hot/cold-конвенция (11 пар).** `rent_deals_act/arch`, `rent_sub_deals_act/arch`, `clients/clients_arch`, `tovar_rent_items/arch`, `karn_brons/arch`, `rent_orders/rent_orders_arch` и т.д. `_arch`-таблицы имеют **другую схему**: те же поля + ведущие `arch_*_id, arch_time, arch_who`. **Не сливать.** MCP-аналитика читает `UNION(active, arch)`; методология зафиксирована 2026-05-14 — менять только по согласованию (есть `LegacyParityTest`).

3. **Времена — Unix timestamp (int), не datetime.** `cr_time`, `ch_time`, `order_date`, `validity`, `react_time` и пр. — секунды Unix. Использовать `FROM_UNIXTIME()` / `UNIX_TIMESTAMP()`.

4. **`rent_orders.phone` = `bigint(15) NOT NULL` без дефолта.** Пустой телефон пишется как `0`; UI показывает телефон только при `phone > 1`. Историческая особенность: **до ~2020 код вставки заявки вообще не имел поля phone** → 100% phone=0 в 2016–2019 (≈8700 архивных записей). С 2020 телефон сохраняется (phone=0 ≈ 1–2%, реальные край-кейсы — контакт в тексте: Viber/Telegram).
   - **`2147483647` — это НЕ sentinel, а INT-overflow.** `rent_orders_arch.phone` исторически был `int(11)` (max 2147483647), тогда как `rent_orders.phone` — `bigint(15)`. Полные номера (`375291234567`) при архивации переполнялись и молча писались как `2147483647` (~11,8 тыс. строк в arch). Исправлено миграцией `2026_06_05_130000_widen_rent_orders_arch_phone` (arch.phone → bigint(15)). Уже переполненные значения восстановить нельзя. Мораль: при любых copy/insert между таблицами сверять типы колонок-источника и приёмника.

5. **Двойная архитектура доступа к БД.** Laravel (`app/`, `routes/`): Eloquent / Query Builder. Легаси (`bb/`): mysqli через `\bb\Db::getInstance()->getConnection()`. **Не смешивать в одном файле.** Легаси-страницы часто делают `foreach ($_POST as $k=>$v) { $$k = get_post($k); }` — variable-variables из `$_POST` (injection-prone); новый код так не писать, использовать prepared statements.

6. **Триггеров и хранимых процедур в БД нет** (проверено локально и на проде 2026-06-05). Вся логика — в PHP.

7. **`php artisan migrate` на проде работает — но вывод `Deploy.php` о нём ничего не доказывает.** С 2026-07-05 по 2026-07-12 он был сломан для ЛЮБОЙ новой миграции: хостинг CloudLinux, на всех PHP-версиях (дефолтный `php` = 8.0.30 через шим `/usr/selector/php-cli`, правильный для проекта `/opt/php74/bin/php` = 7.4.33) был включён **ionCube Loader**, и любой новый файл миграции падал с `PHP Fatal error: Cannot declare class X, because the name is already in use`. Владелец починил это 2026-07-12; с тех пор миграции накатываются штатно (подтверждено на проде: batch 33 — 27.08.2026, batch 37 — 22.09.2026). Поэтому схему меняем **обычной миграцией**, а не ручным `ALTER TABLE` по SSH с последующим `INSERT INTO migrations` — прежний обходной путь больше не нужен.

   Что осталось от той истории:
   - `Deploy.php` печатал `Nothing to migrate.` несколько раз подряд, хотя миграция потом оказывалась применённой, а 27.08 её пришлось накатывать не с первого вызова. **Этой строке верить нельзя** — после каждого деплоя с миграцией смотреть схему явно: `SHOW TABLES` / `SHOW COLUMNS` и таблицу `migrations`. Причину не выясняли.
   - Схема может доехать позже кода. Либо DDL идёт отдельным PR раньше кода, который от него зависит (27.08: #299 → #298), либо новый код переживает отсутствие таблицы/колонки: миграции идемпотентны (`Schema::hasTable`/`hasColumn`), первые чтения обёрнуты в `try/catch` (пример — `bb\classes\SiteSetting`).

8. **Применённый тариф хранится в сделке — прошлое не пересчитывается.** `rent_sub_deals_act`/`_arch` несут `tarif_id`, `tarif_step`, `tarif_value`. Реально заполнен **`tarif_value`** (688 из 701 продлений `type='extention'`), а `tarif_id` почти никогда (4 из 701) — опираться надо на `tarif_value` + `tarif_step`. Расчёт возврата и просрочки берёт **последний применённый** тариф из сделки, а не текущий прайс: `bb/dogovor_new2.php:2807` («вытягиваем последний примененный тариф», `ORDER BY \`from\` DESC` по типам `first_rent`/`extention`/`takeaway_plan`). Значит изменение `rent_tarif_act` НЕ переоценивает уже оплаченные периоды. **Но** форма нового продления строит список из актуальных тарифов модели юнита (`bb/get_item_tarifs.php:44-47` — `rent_tarif_act WHERE model_id = <модель юнита>`) и рядом показывает блок «Последний использованный тариф» с прежней ценой и кнопкой применения (`bb/item_ch_new.php:1014-1022`). Итог: смена модели у юнита или правка прайса меняет то, что оператор увидит по умолчанию при следующем продлении, но подорожания «само» не происходит. Типы sub-deal: `first_rent`, `extention` (продление), `payment`, `cur_return`, `takeaway_plan`, `close`.

9. **`model_id` живёт в 14 таблицах — при удалении или слиянии модели обойти все.** `tovar_rent_items`, `tovar_rent_items_arch`, `rent_model_web`, `rent_orders`, `rent_orders_arch`, `zvonki`, `rent_tarif_act`, `rent_tarif_prev`, `rent_tarif_history`, `dop_photos`, `multi_web`, `favorite_tovars`, `kb_zayavki`, `karnaval_zakaz`. Искать такие колонки надо по шаблону `column_name LIKE '%model%id%'`, а не по точному имени `model_id`: есть ещё `rent_sub_deals_act/arch/arch_deep.sd_model_id` — но это **мёртвая колонка**, заполнена в 0 строках из 517 789 (проверено на проде 2026-07-28). Обратное направление: **карнавальные брони `karn_brons`/`karn_brons_arch` ссылаются на товар через `inv_n` (инвентарный номер юнита), а не через модель** — то есть слияние моделей их не затрагивает, пока не меняются инвентарные номера. `bb/tovar_del.php:266` исторически чистил только `tovar_rent` + `tovar_rent_items` — отсюда 222 висячие заявки, 172 тарифа и 15 фото, разобранные 28.07.2026. Модель с историей (архивные юниты / заявки / звонки) удалять НЕЛЬЗЯ, только сливать в живую или переносить в архив. У категорий правильный путь есть — `Category::archAndDelete()` в `tovar_rent_cat_arch`.

    `rent_tarif_history` при слиянии моделей переносить, а не удалять: это единственный
    источник исторических цен, и удаление ломает `/pricing/snapshot` для дат до слияния.

11. **Модель уходит в `tovar_rent_arch`, а не удаляется** (реализовано 28.07.2026, `bb/classes/ModelArchive.php`). Таблица существовала давно и уже участвовала в фолбэке `UNION(tovar_rent, tovar_rent_arch)` при резолве модели в категорию — `bb/classes/Deal.php:1003,1027,1061,1085` и `bb/classes/tovar.php:1546,1562`, — то есть отчёты были **готовы** к архивной модели, но писать туда было нечем: 0 строк, схема отстала от живой (`price_new` не было, `arch_time`/`arch_who_id` тоже — хотя в `tovar_rent_cat_arch` они есть). Достроено миграцией `2026_07_28_160000_extend_tovar_rent_arch_for_archiving` (+ `arch_snapshot` LONGTEXT).
    - **Почему отдельная таблица, а не флаг `is_archived`.** Флаг проще откатывать и исключает висячие ссылки в принципе, но `tovar_rent` читается в **140 местах в 61 файле** рукописного легаси-SQL — с флагом в каждое надо дописать условие, и пропуск любого означает, что архивная модель молча вылезет в выпадашке, прайсе или на сайте. С отдельной таблицей все 140 запросов ведут себя правильно по умолчанию, а история читается теми 6 местами, где `UNION` уже написан. Плюс это сквозная конвенция проекта (11 пар act/arch).
    - **Что делает архивация:** копирует строку в `tovar_rent_arch` с тем же `tovar_rent_id`, складывает спутников (`rent_tarif_act`, `rent_tarif_prev`, `dop_photos`, `rent_model_web`, `multi_web`, `favorite_tovars`) в `arch_snapshot` (JSON) и удаляет их из живых таблиц, затем удаляет строку из `tovar_rent`. Заявки, звонки, сделки и архивные юниты **не трогаются** — их `model_id` разрешается через арх-таблицу.
    - **Веб-страницу удалять обязательно:** `ModelWeb::getByUrlName()` не фильтрует `status`, поэтому `not_show` L3-адрес не прячет — он продолжил бы отдавать 200. Без строки срабатывает фолбэк `L3Controller::showCategoryWithNotice()` и отдаётся честный 404. Текст страницы не теряется: он в снимке.
    - **Живые единицы товара — жёсткий стоп.** Пока в `tovar_rent_items` есть юниты модели, архивация запрещена: иначе они останутся в остатках и в знаменателе загрузки как фантомный товар (так и вышло со строительным инструментом — 129 чужих юнитов числились в наличии с 2022 г.). Сначала поштучное выбытие в `tovar_rent_items_arch`.
    - У категорий тот же принцип: `Category::archAndDelete()` → `tovar_rent_cat_arch`, а `Category::getById()` читает арх-таблицу фолбэком (`Category.php:351`). Осторожно: `getTovNum()` считает **единицы товара** (`COUNT(tovar_rent_items.cat_id)`), а не модели, поэтому кнопка удаления в разметке появлялась и у категории с моделями без юнитов — серверная проверка `Category::archiveBlockers()` смотрит и модели, и юниты.

12. **Висячие ссылки на удалённые модели чинятся по `inv_n`, а не заглушками.** Разбор 28.07.2026 показал, что «удалённые товары» — это на самом деле **недоделанные слияния дублей**: юниты переносили на правильную модель, дубль удаляли, а заявки забывали. Метод восстановления: заявка помнит `inv_n`, а по инвентарному номеру однозначно известно, какой модели юнит принадлежит сегодня (`tovar_rent_items` + `tovar_rent_items_arch`) — этого достаточно, чтобы вернуть настоящую связь. Так восстановлено 167 из 222 заявок (миграция `2026_07_28_150000_repoint_orphaned_model_refs`). Оставшиеся 55 — веб-заявки с `inv_n=0` **и** `cat_id=0` (модели 257/479/482): товар по данным не определяется, заглушки для них не создавали. Побочная находка: **у заявки `cat_id` — снимок на момент оформления**, он меняется вслед за переездом модели между категориями (у модели 362 заявки несут cat_id 0/9/11, потому что в марте 2018 она уехала из «Качели напольные» в «Колыбель-качели»).

13. **`bb/tovar_del.php:39` — проверка прав не работала (приоритет операторов PHP).** Было `if ($_SESSION['svoi']!=8941 || !$_SESSION['level']>4)`. `!` связывается сильнее `>`, поэтому вычислялось `(!$level) > 4` — всегда `false` при любом уровне. Условие схлопывалось до «залогинен ли вообще», то есть жёстко удалить модель со всеми юнитами мог любой сотрудник. Задумка автора видна из `>4`: только owner (level 5) и coder (level 7). Уровни: `-1` и `0` — курьеры/консультанты, `3` — консультант, `5` — owner, `7` — coder (`logpass.level` + `logpass.main_role`); дефолт `Base::loginCheck()` = `[0, 5, 7]`. Осторожно: **страница `tovar_del.php` нужна сотрудникам для выбытия товара**, поэтому гейтятся конкретные разрушающие действия (`can_destroy()`), а не доступ к странице. Исправлено 28.07.2026.
    - Тогда же закрыт второй путь утечки: кейс «удалить данный товар» жёстко удалял юнит, проверяя только `status='rented_out'`. Теперь удаление разрешено лишь для единицы **без истории** — проверяются `rent_deals_act/arch`, `rent_orders`, `rent_orders_arch` и `karn_brons` по `item_inv_n`; всё остальное идёт через выбытие.

10. **При слиянии моделей меняется только `model_id`, а не собственный PK строки.** В `tovar_rent_items_arch` есть и свой `item_id`, и `model_id` — правится **исключительно** `model_id`; `item_id`, `item_inv_n` и любые ссылки на юнит остаются как есть. Инвентарные номера — то, на что ссылаются сделки (`rent_deals_act.item_inv_n`) и карнавальные брони (`karn_brons.inv_n`), поэтому их переименование сломало бы историю.

14. **Производитель — свободная строка, и логотип бренда цепляется к ней ТОЧНЫМ совпадением.** `tovar_rent.producer` (плюс копии в `tovar_rent_items` и `_items_arch`) — обычный `varchar` без справочника. `Model::getModelIdsArrayByProducer()` делает `WHERE producer='...'`, а на нём стоят `ModelWeb::loadLastProducerLogo()` (подставить логотип бренда новой странице) и `ModelWeb::updateLogoUrlForAll()` (разослать логотип всем страницам бренда) — вызовы в `bb/model_web.php:166,267`. Любой лишний вариант написания отрезает модели от логотипа их же бренда. Producer — ещё и публичная сущность: карточки на главной (`Producer::getAllProducersTovExists()`, кэш `all_producers_tov_exists`, сутки) и **индексируемый лендинг** `/ru/producer?producer=...` с self-canonical (`SearchController::producerFilter()`).
    - **Коллация решает больше, чем кажется.** `utf8mb3_general_ci` игнорирует регистр И хвостовые пробелы (PAD SPACE): `WHERE producer='Chicco'` уже возвращает и `'Chicco '` (78 строк на проде), `'THULE'` уже находит `'Thule'`. Значит варианты по регистру и хвостовому пробелу на поиск и логотипы **не влияют** — это косметика в выпадашках и в отчётах с `GROUP BY BINARY`. А **ведущий** пробел коллация не игнорирует: `' Simple Parenting'` — отдельное значение, отдельная карточка на главной и отдельный лендинг.
    - **Ловушка при чистке:** `WHERE producer <> TRIM(producer)` не найдёт строку с хвостовым пробелом — сравнение их не различает. TRIM применять безусловно, а точечные замены делать через `BINARY producer = '...'`.
    - **URL производителя редиректом из БД не починить:** `CheckRedirects` матчит только путь, без query-строки. Переименования отдаёт 301'ом сам `producerFilter()` по карте `PRODUCER_RENAMED`.
    - Нормализовано 28.07.2026 (`2026_07_28_170000_normalize_producer_spellings`): 8 групп сведены к одному написанию, строк с краевыми пробелами — 0, осталось 326 различных производителей.
    - **Не бренды, а мусор в поле:** `рб` (31 страница), `аксессуар` (19) и `акссесуар` (8 — опечатка того же слова), `Китай`. Требуют решения владельца, не трогали.
    - **107 L3-страниц без логотипа**, хотя у их бренда логотип есть на другой странице (проверено 28.07.2026). Массово не рассылали: часть «брендов» — мусор выше, для них логотип бессмысленен. Штатный путь — `updateLogoUrlForAll()` из админки по конкретному бренду.

15. **`rent_orders.phone_yn` / `fio_yn` — МЁРТВЫЕ колонки, не оживлять.** Заведены под идею «1/0 — такой клиент уже есть в базе» (исходный комментарий сохранился в `bb/classes/bron.php`), но **ни один путь записи никогда не выставлял туда ничего, кроме `''` или `0`** — проверено по всему коду 27.08.2026: их только читают из строки в свойства класса и пишут обратно тем же нулём. Помечены как мёртвые в `bb/classes/bron.php` и `bb/classes/Zayavka.php`. Признак повторного клиента считается **вживую по телефону**, а не флагом в строке брони: данные клиента меняются (слияние дублей `bb/client_merge.php`, новые договоры), закэшированный в заявке флаг протух бы молча. Из схемы не удаляем — колонки участвуют в позиционных `INSERT ... VALUES` (см. п.1) и в явных списках колонок архивации; удаление потребует обхода всех этих мест и отдельного решения.
    - **`bb/bron.php` удалён 27.08.2026** — это был дубль устаревшей версии `bb/classes/bron.php`, объявлявший `class bron` в **глобальном** пространстве имён. Ни одного `require` на него в проекте не было, и в classmap composer'а он тоже не попадал (PSR-4 `bb\` → `bb/` глобальный класс не резолвит). Проверено эмпирически: `php -r 'require "vendor/autoload.php"; require "bb/classes/bron.php"; var_dump(class_exists("bron", true));'` → `false`.

Удаление файла это не сломало — сломано было и до него. Лечится добавлением `use bb\classes\bron;` в файл (в глобальном пространстве имён `use` работает) либо полным именем `\bb\classes\bron::`.

16. **Телефоны клиентов лежат ГОЛЫМИ цифрами, но в четырёх разных видах.** `clients.phone_1`/`phone_2` — `varchar` **без единого не-цифрового символа** (проверено 27.08.2026: `WHERE phone_1 REGEXP '[^0-9]'` → 0 строк). Поэтому `REPLACE(REPLACE(REPLACE(...)))`-лапша в `bb/ajax_client_check.php` и `bb/ajax_client_suggest.php` — защитная шелуха, а не необходимость; `RIGHT(phone_1, 9)` работает напрямую и вдвое дешевле. Зато **один абонент записан по-разному**: `291234567` (9 цифр, 47 523 строки), `0291234567` (10, 1 524), `80291234567` (11, 1 441), `375291234567` (12, 123), плюс российские `79236076387`. Отсюда правило сравнения по **последним 9 цифрам** — оно сводит все эти формы. Осторожно с краями: 464 клиента имеют 7-значные городские номера, они под правило не попадают в принципе, и «повторным» такой клиент не опознается.
    - **Пустой второй телефон — это строка `'0'`, а не NULL и не `''`.** Любое сравнение по `phone_2` должно её отсекать явно, иначе все «пустые» клиенты схлопнутся в одного.
    - **Индексов на `clients` нет вообще, кроме PRIMARY.** Поиск по телефону — всегда полный скан (51 239 строк, ~36 мс на партию из 100 номеров). Значит сравнивать надо **пачкой на всю страницу**, а не по разу на строку: построчно это десятки сканов на один показ списка. Так сделано в `bb\classes\ClientLookup::forPhones()`.

17. **Один и тот же номер бывает вписан разным людям — «повторный клиент» по телефону не абсолютен.** Рекорд на 27.08.2026: `447122445` стоит в `phone_1` у шести разных человек (Демидко, Леончик, Авдонин, Петрович, Курдеко), причём личный `phone_2` у каждого свой — похоже, этим номером затыкали пустое обязательное поле. Хвост небольшой: из 45 493 уникальных номеров 2 331 приходится на две карточки, 134 — на три, 15 — на четыре и больше. Практический вывод: **автоподстановка клиента допустима только при ровно одном совпадении**; на нескольких оператор выбирает сам, а с порога `ClientLookup::SHARED_PHONE_THRESHOLD` номер помечается «общим» и доверия ему нет. Второй сигнал для разбора — фамилия из самой брони (`rent_orders.family`), она заполнена у 76–79 % свежих броней; **у заявок же она почти пустая** (1–2 % в 2023–2025, 47 % в 2026), так что там опереться не на что.

18. **`clients.arch_n` — надёжный счётчик договоров, ему можно верить вместо JOIN'а.** На 51 239 карточек расхождение с реальными `rent_deals_act`/`rent_deals_arch` — 18 строк (10 с договорами при `arch_n=0`, 8 наоборот). Поэтому «клиент у нас реально был» дешевле всего проверять по `arch_n>0`, а таблицы сделок дёргать только для нулевых — обычно это пустой список и лишнего запроса не будет.

19. **Срок аренды, названный клиентом, до 27.08.2026 существовал только внутри текста `info`.** Формат сайта: `«В брони клиент указал: с 02.03.2026 по 01.05.2026 на 60 дня.»` (`L3Controller`) и `«<span class="bk-days">14 дн.</span>»` (`CartController`, отдельный блок на каждую позицию корзины). В архиве 9 145 таких броней. С 27.08.2026 срок пишется в колонки `rent_days`/`date_from`/`date_to`, а для старых записей работает разбор текста (`bron::parseRentPeriodFromInfo()`, распознаёт все 9 145). Две ловушки формата: число дней бывает **пустым** (`«на  дня.»`) — тогда срок добирается из дат; и у 116 записей названные дни расходятся с названными датами больше чем на сутки — приоритет у явного числа дней, по нему считается оплата.

20. **Категория `tyu` = «К УДАЛЕНИЮ» (`tovar_rent_cat_id` 175) — служебная свалка, но 10 её моделей опубликованы.**
    Остаток миграции старого сайта (старые `/karnaval/<slug>.htm` вели именно на её адреса). В категории
    60 моделей: 10 с веб-страницей и единицами (9 карнавальных костюмов и куб-конструктор), около 50
    исторических без страниц и 3 учётные псевдо-позиции (622 «ВОЗВРАТ ДЕНЕГ ПО ОТКАЗАМ», 900 «или аналогичную
    по характеристикам», 1404 «Полина») — на сайт они не предназначены. По цепочке `main_sub_razdel_id`
    категория попадает в `medical-prokat/electroterapiya-prokat`, а в таблице `subrazdel_category` её нет —
    поэтому в меню её не видно, но сайт сам строил ссылки на неё (рекомендации на медицинских страницах,
    поиск, sitemap). Сейчас скрыта механизмом `bb\classes\Category::HIDDEN_CATEGORY_REDIRECTS`
    (`id => адрес редиректа`, сейчас `175 => /ru/karnavalnye-kostyumy`): исключена из рекомендаций,
    поиска, фильтров, sitemap и цены 2ГИС-фида, а карточки и страница категории отвечают 301. Чтобы скрыть
    ещё одну служебную категорию — добавить её `id` в этот список. Это НЕ удаление: модели и единицы на
    месте, админка их видит; для полного удаления нужна архивация (`ModelArchive`, см. п. 11) после
    списания единиц. По данным на 24.09.2026 карнавальных броней (`karn_brons`) по этим моделям за 12
    месяцев нет, обычные заявки в `rent_orders` — есть (11 за год).

21. **Категория модели хранится в нескольких таблицах.** Источник — `tovar_rent.tovar_rent_cat_id`, но
    копия лежит в `tovar_rent_items.cat_id`; в истории — `rent_orders(_arch).cat_id`,
    `tovar_rent_items_arch.cat_id`, `call_demand_items.cat_id`. Админка (`bb/tovar_new_mod.php`) при смене
    категории обновляет первые две; историю не трогает. На 24.09.2026 у 14 единиц `cat_id` уже расходится с
    категорией модели. Переносить модель в другую категорию нужно в обеих таблицах; MCP API этого не
    умеет (пишет только SEO-поля страниц и редиректы).

22. **`rent_model_web.status = 'not_show'` не закрывает прямой адрес.** `ModelWeb::getByUrlName()` статус не
    фильтрует, а L3 открывается по слагу при любом префиксе, поэтому такая карточка отвечает 200. Флаг
    прячет модель из поиска, рекомендаций, листингов и sitemap, но не сам URL. Честный 404 даёт только
    архивация (`ModelArchive` удаляет веб-страницу) или отсутствие единиц (`l3_not_found`). Чтобы закрыть
    целую категорию, не удаляя товары, — п. 20.

23. **Где лежит текстовый контент сайта и чем его править.** Описание карточки — `rent_model_web.main_descr`
    (MCP API: поле `description`, `PATCH /pages/product/{slug}` и `/pages/product/bulk`; история — `GET /pages/history`,
    таблица `mcp_content_versions`). Тексты главной и L2-страниц — таблица `pages` (`level_code` `main`/`category`/…;
    поля `h1_long_text`, `code_block_1`, `code_block_2`, `faq`). **Главная (`pages.id=1`, `url_key='main'`) через MCP API
    не правится** — только админка или прямой UPDATE; `/pages/listing/{slug}` находит лишь страницы существующих категорий
    каталога. В `pages` есть строки без категории (id 22 `detskie-kolyaski`, отдаёт 200 «Раздел не найден.») и строки за
    редиректом (id 25) — их контент мёртв или недостижим. Класс `floatLeft` в CSS сайта не определён (для обтекания
    картинки в описании нужен inline-стиль). Файлы, на которые ссылается контент (`bb/img/*`, `karnaval/img/*`,
    `vesy/img/*`), на проде отсутствуют и в git не отслеживались; ссылки и картинки в контенте проверяются сканом
    текстовых колонок (методика — в отчёте `reply_to_seo_agent_404_audit_2026-09-24.md`).
24. **Модель без единиц отдаёт 404 — решение владельца от 25.09.2026 (остаётся как есть).** Пока в `tovar_rent_items`
    нет ни одной строки модели, `L3Controller` отвечает 404 (`l3_not_found`: фото, «данный товар больше не доступен для
    проката», слайдер «Вам может понравиться»); когда единица заведена — снова 200. Снимок прода 25.09: 77 из 850
    опубликованных моделей (9%) без единиц; последняя единица ушла: продана 48, списана 26 (`out_status='bron_delete'`,
    кнопка «Списать товар» на странице броней), не возвращена 1, ещё у одной единиц не было вовсе; давность: ≤30 дней 21,
    31–90 дней 18, 91–365 дней 35, больше года 2 (сентябрьская волна — списания 4, 7 и 9 сентября: 23 единицы у 23
    моделей). Все пути на карточку требуют наличия единицы: поиск (`ProductSearch`), листинги разделов/подразделов/
    категорий, фильтры возраст/производитель, рекомендации (`Model::getModelIdsArray*`, кэш 60 минут), sitemap; в меню
    моделей нет вообще. Проверено на проде: ссылок на такие модели нет ни на 124 страницах каталога из sitemap, ни на
    43 страницах производителей, ни в текстах `pages`/описаниях, ни в избранном. Остаются только прямые заходы: старые
    ссылки поисковиков, закладки, внешние сайты и рекламные ссылки (не проверялось), а в первый час после ухода последней
    единицы — устаревший кэш рекомендаций. Трафик на такие страницы (лог 16–25.09, строки задвоены): ≈1200 запросов за
    10 дней — Googlebot ≈100, Яндекс ≈90, Bing ≈70, остальное боты и сканеры; из поиска человек пришёл ≈2 раза.
    Рассмотренные и отклонённые варианты: 200 «нет в наличии» с `OutOfStock` на N дней (риск soft-404, сложнее,
    органики почти нет) и 301 на категорию (Google тоже считает soft-404).

## Архитектура заявок (demand requests)

- **Заявка** = `rent_orders.type2='zayavka'` — запрос клиента на товар, которого нет в наличии. **Бронь** = `type2 IN (bron, deliv, remont, out)`. Одна таблица `rent_orders` хранит и то, и другое (+ `stirka`, `sell`).
- **Точки создания (каждая делает звонок + заявку за одну отправку):**
  - `app/Http/Controllers/L3Controller.php` — страница товара (нет в наличии);
  - `app/Http/Controllers/CartController.php` — оформление корзины;
  - `app/Http/Controllers/ZvonokController.php` — модалка заявки / обратный звонок;
  - `bb/zv_ch.php` — кнопка «Оформить заявку» (из звонка).
  - Ядро: `bb\classes\bron::createZayavka()` → `insert()` (чистый INSERT, **без дедупа**).
- **Точки редактирования (через `update()`, безопасно):** `bb/rent_zayavk.php` — действия «сохранить звонок», «недозвон», «самовывоз» (заявка→бронь, `z_to_br()`), «удалить» (`arch_copy()`+`del_br()`). Есть optimistic-lock по `ch_time`/`last_ch_time`.
- **Механизм задвоения:** сайт создаёт `zvonki` (уведомление) + `rent_orders` (заявка) за одну отправку, но **связи между ними нет** (`zvonki` не хранит `order_id`). Оператор в `zv_ch.php` жмёт «Оформить заявку» → создаётся вторая заявка. `Zvonok::addLitZvonok` имеет `isDublicate()`, а `createZayavka` — нет, и уникального индекса в `rent_orders` нет.
- **Soft-delete уже есть по факту:** «удалить» в `rent_zayavk.php` копирует в `rent_orders_arch`, затем удаляет из активной. Страница «Удалённые заявки» — `bb/rent_zayavk_arch.php`.
- **Бейджи** (`bb/bb_nav_badge.php`): «новые» = `type2='zayavka' AND info2 пусто`; «товар появился» = модель снова в наличии.
- **Потребители заявок (read):** `bb/reports.php`, MCP `OperationsController/MarketingController/MetaController/ExportController`. Аддитивные колонки им не мешают.

## Тестирование (как запускать) — findings 2026-06-05

- **Запуск тестов только в контейнере** `tiktakby-app`: `docker exec tiktakby-app php artisan test [--filter=...]`. Причина: `bb\Db` **хардкодит** host `db` (не из `.env`), который резолвится только внутри docker-сети. С хоста (`localhost:33060`) легаси-код к БД не подключится.
- **`bb\Db` — отдельное mysqli-соединение, НЕ Laravel PDO.** Поэтому Laravel-трейт `DatabaseTransactions` его НЕ откатывает: всё, что пишет легаси-код (`bb\classes\*`), на отдельном соединении и не роллбэчится транзакцией Laravel. Для тестов легаси-логики: либо самим чистить за собой в `tearDown()` (собирать созданные id и удалять), либо инъектировать соединение в тестируемый класс и делать `START TRANSACTION`/`ROLLBACK` на нём (но осторожно: `LOCK TABLES` в MySQL неявно коммитит транзакцию — ветки с lock не изолируются транзакцией).
- **Тестируемость легаси:** новые классы (напр. `bb\classes\Zayavka`) принимают **инъектируемое** `\mysqli`-соединение в конструкторе (default `bb\Db::getInstance()->getConnection()`) — чистый DI и контроль соединения в тестах.
- **`phpunit.xml`:** sqlite закомментирован → тесты идут на дефолтном mysql-соединении (та же dev-БД `tiktakby_tiktak`), без глобального RefreshDatabase. Тесты в репозитории на ветке `main`: набор `tests/Feature/Mcp/*` (читают реальные данные, есть `LegacyParityTest` с зафиксированными суммами) + `tests/Feature/ZvonokRedirectTest.php`. (MCP marketing/redirects-тесты живут на ветке rocketsms, на main их нет.)
- Контейнеры проекта: `tiktakby-app` (PHP), `tiktakby-db` (mariadb 10.6), `tiktakby-pma`. Прямой доступ к БД для разовых запросов: `docker exec tiktakby-db mysql -u tiktakby_tiktak -pVai7evahch tiktakby_tiktak -e "..."`.

## Практика работы (по просьбе владельца)

> Владелец писал базу сам ~10 лет, самоучка; в коде есть легаси и неоптимальные решения, особенно ранние. **При каждом удобном случае предлагать мелкие безопасные (low-risk) правки** того кода, который и так трогаем. **Массовый рефакторинг легаси не делать без явного запроса.** Перед добавлением колонок — всегда проверять позиционные INSERT (gotcha №1).
